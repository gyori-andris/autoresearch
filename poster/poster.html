Agent-guided autonomous research and optimisation

Single-cell array I/O as a test case. Gyori Laszlo Andras · Pheiron
Pheiron
1 · Problem and claim
Can a coding agent find and validate real speedups in single-cell I/O?
Reading H5AD, Zarr and SOMA arrays can account for substantial time in single-cell workflows. The cost can sit in the algorithm, the data types or the I/O path: chunk boundaries, metadata round-trips, sparse-index dtypes, decompression, imports and coordinate lookup all contribute, and each is measurable. Profiling one candidate against a baseline is tractable; the cost is repeating that build-test-measure cycle across targets. We use a coding agent to repeat this cycle under a written contract, with a fixed evaluator deciding which changes to retain.
1 · Define the task and its checks. An engineer specifies a target as a contract that names the operation, the allowed edits, the evaluator, the checks and the resource budget. An autonomous agent then runs the experiment loop against that contract, one bounded change per session, and keeps a change only if it passes every check and beats the measurement noise. Within each contract the agent was free to change the algorithm, the data types or the CPU instructions.
2 · Measured gains and rejected attempts. On the named workloads, speedups range from 1.25× (reported) to 20×. Across 14 case studies, eight targets yielded no accepted optimisation; some stopped at the initial checks. AnnData and Scirpy reached native C and CPU-specific kernels; a separate hand-built decoder explores similar techniques.
2 · Experiment design
Loop protocol · one experiment per session
Each session starts from the contract, the retained code and the registry, tests one hypothesis, is scored once by the frozen evaluator, and exits. The harness keeps the candidate only if every gate passes and the gain exceeds the keep threshold; otherwise the retained code stands. Any session can be the last; what is retained then goes to independent replay and human review.
3 · What a contract looks like
One contract, four declarations
Before the first experiment runs, the engineer fixes four things in a contract: what counts as better, what the agent may change, what must not break, and under which conditions results are comparable. The agent reads the contract and must not change it. The example is the contract for AnnData's dense-to-sparse conversion, in the phase that allowed native code.
Every contract
Example · AnnData dense → sparse
Measure
What does better mean?
The evaluator measures time and memory. One score ranks candidates; gates enforce correctness and resource limits. A candidate is kept only if it passes the gates and improves the score by more than the set margin.
Over six test cases, the geometric mean of the candidate's latency divided by the unmodified code's latency; lower is better. Keep threshold 0.02, set from three baseline runs on the same machine; if those runs spread by more than 5 % of their median, the loop does not start.
Surface
What can it touch?
An explicit list of files the agent may edit. Everything else is frozen, including the evaluator, the tests, the benchmark data and the build.
Two files: src/anndata/_io/h5ad.py and, optionally, a native C file, src/anndata/_io/_dense_sparse_native.c.
Gates
What can't break?
Correctness, resource and time checks that all must pass before the score is considered; a failed gate rejects the candidate regardless of speed.
Native build succeeds; upstream tests pass unchanged; output equals the SciPy reference exactly, element by element and in type, shape and dtype; peak memory below 1,536 MB; within 240 s; no result cache, no special-casing of benchmark inputs, no hidden threads.
Machine
When are results comparable?
One pinned machine, one fixed workload and a stated cache condition. Any change of hardware, compiler, dependencies or data invalidates the comparison and requires a new baseline.
One named VM (coffee-skunk-53: AMD EPYC 7B12, 8 vCPUs, GCC 11.4), one core, one thread. AnnData times HDF5 reads and conversion with a warm page cache. H5AD and Zarr measure cloud reads in fresh processes, including materialisation of the requested slice. Six 7,000 × 7,000 float32 cases at three densities and compressions, each to CSR and CSC, timed six times with candidate and reference alternating.
Each contract also declares its resource budget: match the original implementation, impose a ceiling, or permit a stated trade-off. A latency objective alone does not justify a 10–100× memory increase.

The read cost was dominated by converting returned string coordinates to array positions. The fast path is written only when the array fits uint32 positions, is disabled when an update grows the column dimension, and falls back to plain searchsorted for labels longer than eight bytes, where the uint64 cast would collide. Peak memory was logged but not scored. Nine tests cover the fallbacks.

Accepted · machine-specificLocal read · HDF5, warm cache
Workload
Each case reads a dense 7,000 × 7,000 float32 HDF5 dataset slab by slab and converts it to CSR or CSC; timing covers the read and the conversion, not the rest of read_h5ad. Six paired candidate and reference runs per case.
Data
Three deterministic datasets, 0.1 % density uncompressed, 1 % with LZF and 10 % with gzip level 1; each converted to CSR and to CSC, six cases.
Machine
One pinned core of an AMD EPYC virtual CPU (AVX2, no AVX-512), GCC 11.4 with -march=native, one thread, page cache warm.
Contract
The agent may edit h5ad.py and one optional C file. Output must equal the SciPy reference exactly and pass 19 upstream tests; peak RSS ≤ 1,536 MB; 240 s in all. The score is the geometric mean of six median time ratios; kept when it beats the best prior by more than 0.02.
Winning mechanism
A C kernel converts each dense slab to CSR or CSC directly: an AVX2 compare marks nonzero lanes eight at a time, a count pass sizes the output exactly, and an emission pass writes values and indices into it.

Deterministic sequence sets from Scirpy's 3,000-sequence reference fixture, with frozen expected outputs.

The agent may edit the CPU Hamming kernel and a native wrapper with runtime dispatch and a Numba fallback; every timed call is compared exactly against frozen references, and a deliberately reused result must be rejected; kept above a 3 % improvement.
Winning mechanism
A C kernel compiled once per process replaces a Numba function recompiled on every public call; it compares 64 bytes at a time and counts mismatches with a popcount. Where the host lacks AVX-512BW, the Numba path remains.

Discussion
What the results support, and what they leave open
Results. The five main cases use familiar optimisations: they read less data (H5AD), make fewer metadata requests (Zarr), stop recompiling an unchanged kernel (Scirpy), store positions alongside labels (TileDB), and build sparse output directly in native code (AnnData). The loop proposed and tested changes under contracts set by engineers. Implementation review added tests and safeguards.
Measurement. An optimising agent will use any freedom the measurement leaves it. The contract must therefore define what is timed, when outputs must be materialised and which forms of reuse are allowed. Otherwise, the score can reward deferred work or a cached result. The H5AD 7.3× result uses fresh-process GCS reads under a peak-memory gate. AnnData uses a warm page cache to measure HDF5 reads and conversion. AnnData and Scirpy passed exact output checks on their test cases. Wider input coverage and hardware portability remain to be tested.
Machine-specific code. The AnnData and Scirpy loops produced CPU-specific kernels. Wider use requires runtime CPU dispatch, tested fallbacks, package integration and end-to-end checks on representative inputs. In a separate Scirpy comparison, the C port was 18.7× faster than Numba and AVX-512 added 1.085×. The C port changes both compilation behaviour and kernel execution. A kernel built for one instruction set serves few users and adds build and test burden for maintainers, and GPU backends raise the same question. Whether scverse packages would accept such contributions has not been established.
Search. The loop ranks candidates by one score and retains one implementation. Next, we could test richer search strategies: GEPA-style reflection on execution traces (profiler output, failed gates, compiler errors), a maintained set of complementary candidates, scheduling of hypotheses by expected gain, and combining partial improvements across sessions. Under any of these, the frozen evaluator still decides acceptance.
scverse. What transfers is the agent loop. A package's existing benchmarks can serve as its evaluator while maintainers retain the task definition, the allowed edits and the acceptance criteria. The direct test is one maintainer-chosen bottleneck, optimised against upstream main with the project's own tests.
